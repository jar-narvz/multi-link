Board 19 · multi-link in the menu bar

A native SwiftUI menu-bar app (owner, 2026-11-12) that shows what is working, waiting and stale in every repo, with the Claude → Codex hand-offs under the session that made them. It sends the Codex-done notifications under its own name, so the Script Editor step goes away. Clicking a row opens it: the app link, or Phase 18's terminal jump. Its data comes from one long-running multi-link watcher, as with the pane. Pick one option in each part. Rows are example data in the shape of real output.

Comparables

C1VibeBar

A menu-bar monitor for Claude Code, Codex and OpenCode sessions: running, awaiting input, idle, stopped. Works: state at a glance across tools. Awkward: each session stands alone, so it can't show that a Codex run belongs to a Claude session.

C2Agent Signals

Counters in the menu bar for waiting, working and done; clicking a session focuses its iTerm tab. Works: the count is the whole answer most of the time. Awkward: iTerm only, and three numbers take a lot of menu-bar width.

C3OpenAgentPeek

Reads Claude and Codex session files, derives status and context use, and jumps to a session's window (Tauri). Works: no setup. Awkward: a flat list, with no grouping by repo or plan step.

These descriptions come from each project's listing and were not tried here. What multi-link adds: hand-off links (exact / likely), PLAN.md steps, and opening without starting a second copy.

States every option needs

SSetup and errors

multi-link not found (the app can't see the binary; it says which path it tried). Too old (the binary has no watcher for the app). Notifications off (shown once, with a button that opens System Settings → Notifications). Watcher stopped (keeps the last data with its age, and retries).

NNotifications

Same text as Phase 17: codex finished (18.3) plus the start of the final message, now credited to multi-link. The pane leaves these to the app while it runs, and each hand-off still fires once (the marker files in ~/.multi-link/notified/).

Colours follow boards 16–18. Not decided here: launch at login (proposed: off, with a toggle) and signing. The app is built and ad-hoc signed locally, never notarized or published; Step 19.0 checks that macOS allows notifications from an ad-hoc signed bundle.
